# Context Engineering

上下文不是“把整个仓库塞给模型”，而是有来源、优先级和预算的编译过程。`ContextBuilder` 按全局指令、workspace 根指令、`.yfh` 项目指令、会话消息、手动附件和最多三个自动提及文件组织内容；所有文件仍受 workspace 边界和大小限制。

预算先为系统指令、当前请求和回答预留空间，再选择历史与文件。没有专用 tokenizer 时使用明确标记的近似估算。达到阈值后，旧历史压缩成八字段结构：目标、已完成、关键决策、约束、文件、测试、未解决问题、下一步。最近消息和关键约束保持原文；桌面“立即压缩当前会话”、CLI `yfh sessions compact <session-id>` 或 TUI `/compact` 可手动触发。

SQLite v5 把结构化摘要随会话保存。下一次运行会先恢复摘要，再附加最近原始消息；如果再次压缩，旧摘要字段与新内容确定性合并，避免否定约束随多轮摘要漂移。摘要只是请求上下文的加速层，不会删除 `messages` 表中的原始历史。工具 schema 在一次构建中只估算一次，最近消息用二分法选择，避免长会话逐条试删。

自动提及只是一种低成本启发式，不替代搜索或索引。`/add` 是用户明确授权加入上下文，`/context` 展示来源与估算，让“模型看到了什么”可解释。

## 我应该理解什么

上下文选择、排序、预算与压缩是 Harness 的核心产品行为。

## 我可以修改什么来做实验

调整自动文件上限或压缩阈值，比较请求快照和答案变化。

## 常见 Bug

指令顺序反转、附件越界、摘要丢失否定约束、估算后仍超模型窗口。

## 面试可能如何提问

如何在有限上下文中保留任务连续性？摘要怎样避免语义漂移？

## 一个动手练习

构造超预算会话，验证“禁止修改某文件”在压缩后仍被保留。
